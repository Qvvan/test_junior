# Схема управления ограничениями доступа

В проекте используется простая ролевая модель доступа (RBAC): права выдаются не по отдельным действиям, а по роли пользователя.

## Какие роли есть сейчас

- `user` — обычный пользователь.
- `admin` — администратор.

Роль хранится в аккаунте и дублируется в JWT access token (поле `role`).

## Как проходит проверка доступа

1. Пользователь логинится (`/api/v1/auth/login`) и получает пару токенов: `access` и `refresh`.
2. Для защищенных ручек клиент передает `Authorization: Bearer <access_token>`.
3. Зависимость `require_role(...)`:
   - проверяет наличие и формат bearer-токена;
   - декодирует JWT и валидирует тип токена (`type = access`);
   - читает `sub` (id аккаунта) и `role`;
   - дополнительно проверяет, что аккаунт активен в БД;
   - сверяет роль пользователя со списком разрешенных ролей для конкретного endpoint.
4. Если роль не подходит — возвращается `403 Forbidden`, если токен невалидный/отсутствует — `401 Unauthorized`.

## Матрица доступа по текущим endpoint

### Доступ без авторизации

- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/refresh`
- `POST /api/v1/auth/logout`

### Доступ для `user` и `admin`

- `POST /api/v1/auth/change-password`
- `GET /api/v1/user/me`
- `PUT /api/v1/user/me`
- `DELETE /api/v1/user/me`

### Доступ только для `admin`

- `GET /api/v1/user`
- `POST /api/v1/user/{account_id}/deactivate`
- `POST /api/v1/user/{account_id}/activate`
- `PATCH /api/v1/user/{account_id}/password`

## Почему схема рабочая

- Правила централизованы: доступ задается в одном месте через `require_role(...)`.
- Даже при валидном токене деактивированный аккаунт не пройдет проверку.
- При смене пароля и деактивации аккаунта refresh-токены отзываются, что снижает риск повторного входа по старым токенам.

## Как расширять дальше

- Если появится новая роль, ее нужно:
  - добавить в доменную модель ролей;
  - разрешить в БД (ограничение `CHECK` по полю `role`);
  - явно включить в `require_role(...)` для нужных endpoint.
- Если нужны более тонкие права (например, "может редактировать только часть данных"), можно оставить роли как базовый слой и добавить дополнительные бизнес-проверки в сервисах.
